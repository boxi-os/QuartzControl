# Dark Mode, Kontrast und Farbkonventionen

Aus CLAUDE.md ausgelagert (2026-09-02): die Messungen und Beobachtungen hinter den Regeln, wortgleich. Die Regeln selbst stehen in CLAUDE.md; hier steht, welches Experiment sie erzwungen hat. Neue Einträge kommen mit derselben Form dazu: was gemessen wurde, was daraus folgt.

**Dark mode** is automatic via Tailwind's `darkMode: 'media'` — style new UI with `dark:` variants. The app's own Hell/Dunkel/Systemeinstellung switch does **not** change that: `electron/main/theme.ts` sets `nativeTheme.themeSource`, which flips the *renderer's* `prefers-color-scheme` as well — measured against this repo's Electron binary (OS on dark: `themeSource='light'` made the page report light, `'system'` gave dark back), and verified end to end in the running app for all three states, live and without a reload. So the class strategy was never needed and every existing `dark:` variant kept working untouched; the native dialogs (host-key confirmation, file pickers) follow the app's setting too, which a renderer-only toggle could not have done. Three things go with it: the preference is applied in `whenReady` **before** `createWindow()` (otherwise the first frame is painted in the OS appearance), `BrowserWindow`'s `backgroundColor` is a creation-time option so `applyTheme` calls `setBackgroundColor` on the open window as well (the old colour otherwise flashes through on resize), and the save handler applies it only when the payload actually carries a `theme` key — an absent key and an explicit `'system'` are indistinguishable after crossing IPC, so a partial save from elsewhere would silently reset the window.
- **`color-scheme: light dark` on `:root` is what makes the *native* half of the UI follow the switch.** Everything above only reaches surfaces our own classes paint; the popup a `<select>` opens is drawn by the UA on a separate surface, and without the declaration it draws it for a light page always. Measured on Linux in dark mode: white popup, white option text, an entry readable only while hovered. macOS hid it because the popup is drawn by the OS there, which is a reminder that "checked both schemes" on one platform is not the same as checked. `light dark` means "follow `prefers-color-scheme`", which `nativeTheme.themeSource` drives - so this follows the app's own Hell/Dunkel/Systemeinstellung and not only the OS. **It is necessary and not sufficient**: measured in the packaged app on Debian 13 with the declaration in place and the page reporting `prefers-color-scheme: dark` (`getComputedStyle(document.documentElement).colorScheme` → `"light dark"`, `matchMedia('(prefers-color-scheme: dark)').matches` → `true`), the list a `<select>` opens was *still* painted light - Chromium draws that popup in the browser process from the platform theme rather than from the page. The option text does inherit from the `<select>`, which our classes set to near-white in dark mode, so the result was white on white, readable only under the hover highlight. Explicit `background-color`/`color` on `select option` is what Chromium honours there; it is ignored on macOS, where the popup is a native menu - which is why this whole class of bug is invisible during development here.
- `index.css`'s scrollbar rule was `.dark ::-webkit-scrollbar-thumb` — with `darkMode: 'media'` there is no `.dark` class anywhere in this app's DOM, so the dark thumb had never once rendered. It is a `@media (prefers-color-scheme: dark)` block now, which the switch above also drives.
- **Playwright emulates a colour scheme by default, which overrides `prefers-color-scheme` in the renderer** — so through `run-desktop`'s driver the app always rendered light regardless of macOS or this setting, and dark mode could not be verified at all. The driver grew a `colorscheme none` command that clears the emulation; use it before judging anything about appearance.
- **There is one muted-text token, `text-slate-500 dark:text-slate-400`, and a bare light-mode class is the bug.** The app had accumulated three conventions for the same role — a bare `text-slate-400`, a bare `text-slate-500`, and `text-slate-400 dark:text-slate-500`, which goes *darker* on a dark ground. Measured with a WCAG pass over all 19 screens in the running app: the sidebar's group headings and the Übersicht's tile labels sat at 2.25:1/2.56:1 in light and 3.14:1 in dark, and the plugin list's drag handles at 1.48:1 from the same inversion (`text-slate-300 dark:text-slate-600`). The 20 uppercase micro-labels go one step further, `text-slate-600` in light, because at 11–12px they usually sit on the page ground (`#f5f5f7`) rather than on a white card, where slate-500 only reaches 4.18:1. **An always-dark surface takes no `dark:` variant at all** — the empty log console is `bg-slate-950` in both schemes, so `text-slate-400` there is the whole answer. What is left after this is a floor of 4.36:1 in light: that is slate-500 on `#f5f5f7`, and closing the last 3% would mean either flattening the type scale (slate-600 is already the body-secondary tone) or lightening the ground the cards sit on, which is a design decision rather than a fix.
- **A disabled button still has to say what it is.** `disabled:bg-blue-300`/`red-300` with the enabled state's white label measured 1.80:1 and 1.83:1 — the word was simply not there, and on Updates, Git-Sync and Veröffentlichen that word is the only thing naming the action you cannot take right now. Disabled primary/danger carry `blue-800`/`red-900` now; the dark disabled fills are near-black, so white stays there. WCAG exempts inactive controls, which is exactly why this had gone unnoticed — it is a legibility bug, not a compliance one.
- **Every avatar colour is a shade white can be read on.** The project card's initial is always white; the 500-level palette it was drawn on ran from 4.2:1 (violet) down to 2.1:1 (amber), so whether you could read your project's letter came down to what its id hashed to.
