# Electron-Laufzeit, Toolchain, Packaging und App-Identität

Aus CLAUDE.md ausgelagert (2026-09-02): die Messungen und Beobachtungen hinter den Regeln, wortgleich. Die Regeln selbst stehen in CLAUDE.md; hier steht, welches Experiment sie erzwungen hat. Neue Einträge kommen mit derselben Form dazu: was gemessen wurde, was daraus folgt.

**Native macOS chrome, and only there**: `titleBarStyle: 'hiddenInset'` hides the OS title bar in favor of inset traffic lights over a custom header, so any full-width header/sidebar element that should be draggable needs the `.titlebar-drag` CSS class (defined in `src/index.css`), and any interactive control inside a drag region needs `.titlebar-no-drag` or it stops receiving clicks. Windows and Linux get `titleBarStyle: 'default'` — a real title bar above the window — so the 48px drag strip every full-height screen reserves for the traffic lights has no job there - but it is **16px rather than zero**, which is what it used to be: measured on Debian, the first line of every screen sat flush against the native menu bar, and a layout with no separation at all from the OS chrome above it reads as a rendering fault. The non-mac strip is deliberately not draggable, since the real title bar above it already does that. `src/utils/platform.ts`'s `titlebarStripClass` is that strip's one definition (four screens use it); it reads `window.quartzGui.platform` **off the preload bridge, not over IPC**, because the answer is needed during the first render and an async one would paint the wrong layout and then jump. The same file's `isInsideDirectory()` exists for the other half of that mistake: a path prefix test written as `` startsWith(`${dir}/`) `` is silently always false on Windows, which is what hid Vorschau & Build's "Ordner öffnen" button there.

**Electron 43 (Chromium 150, Node 24.18.1), and the upgrade from 33 was not optional.** Electron maintains only its latest three majors, so 33 had long stopped receiving security fixes; it also shipped Node 20.18.3, which Quartz refuses outright (`engines.node >= 22`, checked by its own CLI with an explicit message) — so 33 could never have run Quartz through Electron's embedded Node. The upgrade was verified rather than assumed: all 38 smoke-test visits clean, `nativeTheme.themeSource` still flips the renderer's own `prefers-color-scheme` in all three states, `safeStorage` reports secure, the menu and Cmd+, work, and the dev-server preview iframe loads real Quartz content *through* both the CSP `frame-src` and its `sandbox`. Of Electron 34–43's breaking changes, none touch the 33 Electron APIs this app uses (PDF WebContents, cookie change causes, Linux `showHiddenFiles`, OSR scale factor, `UNNotification`, `clearStorageData` quotas, `hslShift` — all unused).
- **From Electron 42 on the package no longer downloads its own binary.** `electron`'s package.json has no `scripts` field at all any more, only an `install-electron` bin. `scripts/postinstall.mjs` therefore runs `node_modules/electron/install.js` *and then* `brand-electron.mjs`, in that order, skipping either cleanly when it is absent (a `--omit=dev` install has no electron) and never failing the install — a developer without network still gets a working checkout. Without this a fresh `npm install` leaves no `dist/`, and `npm run dev`, the run-desktop driver and `smoke.mjs` all fail in ways that read like a broken checkout rather than a missing step.
- **The first launch of a freshly downloaded Electron binary is slow on macOS** — the OS verifies the signature of a ~300MB bundle before running it, measured at over ten seconds right after the upgrade against ~250ms for every later launch. `smoke.mjs` waits 60s for the first render for exactly this reason; a tighter wait turns "you just bumped Electron" into a failing smoke run.

**Build toolchain: vite 7 + electron-vite 5 + @vitejs/plugin-react 5**, which is where `npm audit` reaches zero. plugin-react 6 already requires vite 8 and electron-vite does not accept that yet, so 5 is the top of the compatible set. `diff` was a runtime dependency imported by nothing (and therefore shipping in the asar) and is gone; react-router-dom 7 is a version bump only, since nothing here uses a data router, a loader or `useFetcher` and v7 keeps `react-router-dom` as a re-export shim - the four `<Navigate>` redirects were re-checked in the running app because relative `..` resolution is the one thing v7 could have changed.
- **`brand-electron.mjs`'s "am I done" test is all three conditions, not one.** electron's own install step re-extracts the zip whenever it decides the install is stale, which puts a fresh `Electron.app` next to the branded one *and* points `path.txt` back at it. Checking only for `QuartzControl.app` therefore reported success while every `npm run dev` after any `npm install` launched the unbranded copy, with 276 MB of duplicate bundle beside it (measured). It now requires the branded bundle, the absence of the fresh one *and* a matching `path.txt`, drops the superseded bundle, and repairs a `path.txt` that lost track on its own.

**Packaging** (`electron-builder.yml`, `npm run dist`): macOS dmg+zip for arm64 and x64, Linux AppImage+deb. **Windows is deliberately absent** — directory symlinks need elevated rights there (which is the Obsidian-vault feature), `npx`/`npm` are spawned through `cmd.exe` so free-text arguments like a plugin source or `--output <dir>` would be reinterpreted, and rsync has no equivalent; an installer for that would package a version that does not work. `files` lists `build/icon.png` explicitly because the main process resolves it at runtime through `app.getAppPath()` (i.e. from inside the asar). `npmRebuild: false` — nothing here compiles against Electron's headers, ssh2 falls back to pure-JS crypto. `identity: null` leaves the bundle **unsigned**: there is no Developer ID, and an ad-hoc signature is treated no better, so first launch needs `xattr -dr com.apple.quarantine` or an open-from-context-menu. `externalizeDepsPlugin()` means everything under `dependencies` is a runtime `require` and has to travel — that is why `typescript` (used at runtime by `pluginSchemaService`) is a dependency and not a devDependency.
  - **The `deb` target needs `ar`, which a minimal Debian does not have.** electron-builder shells out to fpm, and fpm assembles a `.deb` with `ar` from **binutils** — a package Debian's own installer does not pull in for a desktop system. Measured on Debian 13 arm64: the AppImage builds fine, then the deb step dies with `Need executable 'ar' to convert dir to deb` and `npm run dist:linux` exits non-zero *after* having produced a working AppImage, which reads like a total failure and is not one. `sudo apt install binutils` is the whole fix. Nothing in this repo can paper over it — fpm is downloaded by electron-builder at build time and looks the tool up on PATH.
  - **Ohne GL-Kontext kommt kein erster Frame, und mit `show: false` heißt das: kein Fenster (2026-09-03).** Auf Debian 13 in einer VM startete die gepackte App und zeigte nichts - vier Startversuche, vier vollständige, unsichtbare Instanzen mit Haupt-, Renderer- und GPU-Prozess. Im stderr stand kein einziger Fehler aus dem Hauptprozess, nur `eglCreateContext ES 3.0 failed with error EGL_BAD_ATTRIBUTE`, der sich beendende GPU-Prozess und ein Renderer, der mit `--use-gl=disabled --ozone-platform=wayland` weiterlief. `ready-to-show` feuert erst, wenn der Renderer einen Frame gemalt hat; unter Wayland ohne GL kam der nie. Das Fenster wird deshalb auf drei Wegen sichtbar: `ready-to-show` (Normalfall, verhindert das Aufblitzen eines leeren Fensters), `did-finish-load` plus eine Sekunde Nachlauf (das Dokument ist geladen, auch wenn nichts gemalt wurde) und ein Fünf-Sekunden-Timer als letzte Instanz; die beiden Rückfälle schreiben eine Zeile ins Log. Gegengeprüft, indem der `ready-to-show`-Hörer vorübergehend abgeschaltet wurde: das Fenster kam über `did-finish-load`, und auf gesundem macOS gewinnt weiterhin der erste Frame (kein Rückfall im Log).
  - **A VM without an OpenGL context is not an app fault, and it looks like one.** Launching the packaged app on Debian 13 in a VM prints a wall of `ANGLE Display::initialize error 12289: Could not create a backing OpenGL context`, `eglInitialize OpenGL failed` and `Exiting GPU process due to errors during initialization` - after which Chromium falls back to software rendering. That fallback is what the alpha test saw as the window going blank on a resolution change and taking a long time to come back. Nothing here can fix it and nothing should try: `app.disableHardwareAcceleration()` would take the GPU away from real machines to paper over a virtual one. Worth knowing when reading any Linux report, because these errors appear on stderr of every launch from a terminal and read like a crash.
  - **An AppImage needs FUSE 2 at *run* time, and Debian 13 ships only FUSE 3.** The file is built and complete but refuses to start with a `libfuse.so.2` error; `sudo apt install libfuse2t64` fixes it, and `./QuartzControl-*.AppImage --appimage-extract-and-run` is the way around it without installing anything. Unrelated to the build machine — it is the *running* machine that needs it.
  - **`syncDesktopName: true` plus `desktopName` in package.json**, because otherwise the installed launcher is `quartz-gui.desktop` (from `name`) while the window Electron opens calls itself QuartzControl, and a desktop environment cannot connect the two: generic icon in the taskbar, and pinning it pins nothing. This is electron-builder's own fix for it and becomes its default in v27; it is what the `electron uses desktopName as app_id / WM_CLASS` warning during a Linux build was asking for. **Measured on Debian 13 arm64 (X11) after installing the deb**: `xprop WM_CLASS` reports `"quartzcontrol", "quartzcontrol"` against an installed `quartzcontrol.desktop`, the dock shows the app's own icon, and a pinned launcher still works after the app is closed - so the two halves do find each other. Worth re-measuring if `desktopName` or `executableName` ever changes, since the name Electron reports is not derived from the same field as the file it has to match.

**A packaged app finds no `node`, and that is invisible in development.** Every external command here — `npx quartz`, `npm install`, `git` — is looked up on PATH. A bundle started from the Dock, Finder or a desktop launcher inherits launchd's PATH (`/usr/bin:/bin:/usr/sbin:/sbin`) rather than a shell's, and node is in none of those directories: Homebrew uses `/opt/homebrew/bin`, nvm `~/.nvm/versions/<version>`, volta/fnm/asdf/mise their own shims. So every build, plugin install and project creation would fail with ENOENT while the same app run from a terminal worked. `environmentService.ensureToolPath()` runs once in `whenReady` **before `createWindow()`** and patches `process.env.PATH`, so every existing spawn keeps working unchanged instead of each caller threading an environment through. It asks the user's own login shell first (`$SHELL -ilc`, marker-delimited because dotfiles print greetings, 5s timeout because one could wait for input) since a version manager's shim directory is not at a fixed path, and only then probes known install locations. A no-op when node is already findable — every `npm run dev` — and ~60ms when it runs (measured). Verified end to end against the *packaged* app launched with launchd's PATH: `npx` is not found from that environment at all (`env -i PATH=… npx quartz build` → "No such file or directory") while the app resolves node via the login shell and completes a real build.
- **`settings.environment()` probes by running each tool, not by looking for the file.** `/usr/bin/git` exists on a macOS without the Xcode command line tools as a stub that opens an installer, so a presence check reports git as available on exactly the machines where it is not. The start screen shows it in two presentations, never both: a full-width band when something is wrong (the rule `ProjectDashboard`'s attention band follows) and one quiet line in the side column when it is fine — a broken environment must not sit in a 320px column that collapses below the project list on a narrow window.
- **`safeStorage.isEncryptionAvailable()` is not the whole question on Linux.** Without a running keyring Electron falls back to the `basic_text` backend, which encrypts with a hardcoded key and still reports available — so an SFTP password or the GitHub token would land in `connections.json` effectively in the clear with nothing saying so. `connectionsService.getSecretStorageInfo()` reads `getSelectedStorageBackend()` (Linux-only API) and the band says it out loud. The **healthy** line names the backend too, on Linux only: an absent warning and protected secrets look identical, which is exactly what the alpha test asked about a Debian machine, and the backend is the one fact that settles it. Same "cannot check ≠ fine" distinction as `styleService`'s `unavailable` and `updateService`'s `'unknown'`.
- **A menu item that needs the renderer to navigate goes through `IPC.appNavigate`.** The menu is built in main and the routes live in a `HashRouter`, so there is no other way across; `App.tsx` installs the one listener for the app's lifetime, the same shape as the log subscriptions. Today its only user is Settings (Cmd+, / Ctrl+,), which sits in the app menu on macOS and at the top of Datei everywhere else. The Help menu is macOS-expected and was missing entirely; it is also the only place that answers "where does the truth live" and "where is my data" from anywhere in the app rather than only from the start screen. The menu lives in `electron/main/menu.ts` rather than in `index.ts` because it has to be **rebuilt when the language setting changes**: it is built once from a snapshot of `resolveMainStrings()`, so the Sprache select switched the whole renderer instantly and left Datei/Bearbeiten/Ansicht in the launch language until a restart — verified by capturing the macOS menu bar before and after. `applyAppMenu()` rides along on the settings save the same way `applyTheme` does, guarded by the key being present.

**Quartz und npm laufen unter Electrons eigener Node-Laufzeit (Phase 7a, 2026-09-03).** Electron 43 trägt Node 24.18.1, was Quartz' `engines.node >= 22` erfüllt — die Voraussetzung „Node 22 muss installiert sein" war also nie eine echte, es zeigte nur nichts auf das, was schon da war. Der Weg dorthin ist ein Verzeichnis mit drei generierten Shell-Skripten (`node`, `npm`, `npx`) vorn im PATH, **nicht** ein Umschreiben der zwölf npm/npx-Spawns: `sh -c node install.js` in einem Install-Skript weiß nichts von dieser App und kann nur von einem `node` im PATH bedient werden — sobald das existiert, ist jede weitere Umleitung überflüssig, und `buildService`, `runCommand` und die fünf Services darüber fragen unverändert nach `npx`. Die Shims werden bei **jedem** Start neu geschrieben, nicht nur wenn sie fehlen: sie tragen einen absoluten Pfad auf die Electron-Binärdatei, und im AppImage liegt der unter einem Mount-Punkt, der sich pro Start ändert. Die Vorlage steht in `resources/runtime/shim.sh`, weil `scripts/check-runtime.mjs` dieselbe füllt — ein Shim, der von dem gemessenen abweicht, würde die Prüfung wertlos machen.
- **Der Loader (`-r resources/runtime/defaultapp.cjs`) ist eine Zeile mit einem gemessenen Grund.** yargs entscheidet in `hideBin()` über `process.versions.electron && !process.defaultApp`, wie viel von argv es abschneidet (`isBundledElectronApp()` in `yargs/build/lib/utils/process-argv.js`), und `ELECTRON_RUN_AS_NODE` erfüllt beide Hälften. Gemessen gegen das echte CLI: `quartz plugin list` gab die Hilfe aus, weil yargs den Skriptpfad als Kommandonamen las; mit `process.defaultApp = true` listet es Plugins. Der Loader lügt gegenüber jeder Bibliothek, die Electron erkennen will, nicht nur gegenüber yargs — deshalb steht er in einer Datei mit genau dieser Begründung.
- **`ensureToolPath()` sucht jetzt nach git, nicht nach node.** Der Kurzschluss („PATH reicht schon") hing an `findExecutable('node')`, und mit den Shims im PATH ist der immer erfolgreich — die Suche hätte also aufgehört, bevor sie das Verzeichnis mit git erreicht, und eine gepackte App aus dem Dock hätte gar kein git gefunden. git ist ohnehin das einzige Werkzeug, für das diese Suche noch da ist.
- **Was von außen kommen muss, sagt die App jetzt getrennt.** `ToolInfo.source` trennt `'embedded'` von `'host'`: die Zeile auf der Startseite liest „Werkzeuge bereit · in der App: node 24.18.1, npm 11.17.0 · vom System: git 2.50.1", und das Warnband gibt den git-Installationshinweis nur, wenn ein Host-Werkzeug fehlt — fehlt ein eingebettetes, ist die App-Installation unvollständig, was ein anderer Satz ist. Gemessen wird weiterhin durch Ausführen, nicht durch Dasein: der Shim ist das, was die Spawns benutzen, also ist ein Shim, der sich nicht ausführen lässt, genau der Fehler, der gezeigt werden muss.
- **Der Ausweg ist eine Einstellung, kein Automatismus:** `nodeRuntime: 'embedded' | 'system'` (Vorgabe `embedded`), angewandt beim Start und nach jedem Speichern, wie `applyTheme` und `applyAppMenu`. „Host zuerst" wäre für Node falsch, obwohl es für git richtig ist: Node hat eine harte Untergrenze und ein Quartz-Projekt bringt eine `.node-version` mit `v22.16.0` mit, die fnm, nvm, asdf und mise **pro Verzeichnis** auflösen — und jeder Spawn hier läuft mit `cwd` = Projekt. Die Laufzeit hinge damit am Versionsmanager des Nutzers und an einer Datei, die keiner von uns geschrieben hat. git ist der umgekehrte Fall: keine Versionsuntergrenze, aber Konfiguration und Zugangshelfer des Nutzers. Der gemeinsame Satz: es gewinnt die Quelle, die die Anforderung garantiert erfüllt. Der Schalter bleibt für den einen Fall, der ihn braucht — ein Paket, das mit node-gyp kompiliert werden muss und echte Node-Header verlangt.
- **npm reist als eigene Kopie mit, und electron-builder lässt drei Viertel davon liegen, wenn man es nur einmal einträgt.** `createFilter()` in `app-builder-lib/out/util/filter.js` gibt für das *eigene* `node_modules`-Kind einer Kopierquelle unbedingt `false` zurück, vor jedem Muster — `filter: ['**/*']` ändert daran nichts. Mit einem Eintrag kam npm als 4 MB statt 16 an und sein `npm-cli.js` konnte keine einzige Abhängigkeit auflösen. Zwei Einträge (`node_modules/npm` → `npm`, `node_modules/npm/node_modules` → `npm/node_modules`) legen die Kinder unter die Regel: 1938 Dateien rein, 1938 raus, verschachtelte node_modules inklusive. In der Entwicklung unsichtbar, weil npm dort aus dem Repo aufgelöst wird — der Grund, warum diese Phase in einer Messung an der gepackten App endet und nicht in einem Build.
- **Am gepackten Bundle gemessen** (`release/mac-arm64`, `--dir`): es schreibt Shims in seine eigenen Resources, sein npm antwortet 11.17.0, und `npx quartz build` über diese Shims emittiert 114 Dateien mit einem PATH aus Shim-Verzeichnis plus `/usr/bin:/bin` — also auf einem Rechner ohne jedes Node (`/usr/bin/node` gibt es auf macOS nicht). Ein `install`-Skript, das ein blankes `node` aufruft, landet auf derselben Laufzeit (`v24.18.1 | …/QuartzControl.app/Contents/MacOS/QuartzControl`). npm gibt seinen Kindern `npm_node_execpath`, was jetzt die App-Binärdatei ist und eine GUI starten würde — aber `ELECTRON_RUN_AS_NODE` wird vom Shim exportiert und den ganzen Baum hinab geerbt, also bekommt auch das Node.
- **Sechs Wege sind gefahren, einer bleibt offen.** Build (114 Dateien), Dev-Server (HTTP 200, Websocket-Port offen, `Detected change, rebuilding... Done rebuilding in 646ms` — chokidar und `@parcel/watcher` arbeiten also unter Electrons Node, und das Stoppen über die Oberfläche räumt den neuen Prozessbaum auf), Plugin-Unterkommando, `npm install` mit Lifecycle-Skript, ein komplettes `quartz create` in einem Wegwerf-Ordner (Klon → `npm install` → Wizard → Aufwärm-Build mit 58 Dateien, alle vier geprüften N-API-Module vorhanden) und das gepackte Bundle. **Auf Debian 13 arm64 vom Nutzer nachgefahren (2026-09-03) und ohne Befund**: Umgebungszeile, das Umschalten der Laufzeit in beide Richtungen, Build, Dev-Server samt erkannter Dateiänderung (dort also `@parcel/watcher`/inotify statt fsevents), ein `npm install`-Weg und das gepackte AppImage. Offen bleiben nur die Netzwege (Theme-Marktplatz, `quartz upgrade`) mit den Registry-Einstellungen eines echten Nutzers. Nebenbei aufgefallen und *nicht* von der Einbettung verursacht: npm 11.17 führt Install-Skripte nur nach ausdrücklicher Freigabe aus (`npm warn allow-scripts`) — sharp und esbuild kamen trotzdem vollständig an, weil sie Prebuilds mitbringen, aber ein Paket, das sein Skript wirklich braucht, würde hier hängenbleiben, unabhängig von der Laufzeit.

**git reist mit, weil die Alternative auf macOS mehrere Gigabyte sind (Phase 7c, 2026-09-03).** git ist die einzige Voraussetzung, die Quartz selbst stellt: das Paket `@jackyzha0/quartz` ist unveröffentlicht, der offizielle Weg *und* `createService.ts` ist ein `git clone`; Quartz installiert Plugins mit `git clone --depth 1` (`quartz/cli/plugin-git-handlers.js`), `upgrade` und `sync` sind git-Kommandos, und der Snapshot-Store ist ein eigenes Git-Repo. Ohne git ist ein Quartz-Projekt also nicht einmal entstehbar — nur bearbeitbar und veröffentlichbar. Für einen Einsteiger auf einem frischen macOS heißt „git installieren" trotzdem: Xcode-Kommandozeilenwerkzeuge, mehrere Gigabyte, für einen Klon. Deshalb liegt eines bei.
- **Von 141 MB sind 26 MB git.** Quelle ist dugite-native v2.53.0, derselbe Build wie in GitHub Desktop. Im macOS-Bundle sind **104 MB** der Git Credential Manager samt .NET-Laufzeit und 12 MB git-lfs; das Linux-Bundle (52 MB) hat keinen GCM, dafür 12 MB Übersetzungen, die das macOS-Bundle gar nicht mitbringt. git selbst ist 3,3 MB, die 414 Einträge in `libexec/git-core` sind Symlinks darauf. Nichts davon ist von hier aus erreichbar — Zugangsdaten laufen über `GIT_ASKPASS`, Quartz-Inhalte sind Markdown —, also wirft `scripts/fetch-git.mjs` GCM, git-lfs, `share/locale` und `share/gitweb` weg. **Nach Namen, nie nach Größe**: eine Größenregel würde beim nächsten git-Release still etwas anderes wegwerfen. Die Fassung ist eine Konstante, und die `.sha256` des Releases wird vor dem Auspacken geprüft — ohne das wäre es „lade irgendetwas aus dem Netz und pack es in die App".
- **Das Bundle braucht zwei Umgebungsvariablen, sonst sucht git unter `/`.** Mit `env -i PATH=/nonexistent` bricht `git clone` mit „unable to find remote helper for 'https'" ab; mit `GIT_EXEC_PATH` und `GIT_TEMPLATE_DIR` laufen `clone` über HTTPS, `init`, `commit` und `log` durch. `GIT_SSL_CAINFO` nur dort, wo das Bundle einen eigenen Zertifikatsspeicher mitbringt (Linux); macOS holt die Wurzelzertifikate über Secure Transport. **Auf Debian 13 arm64 vom Nutzer nachgemessen (2026-09-03)**: mit einem PATH ohne git löst die installierte `.deb`-App auf das Bundle 2.53.0 auf, und ein neues Projekt anzulegen läuft durch - der Klon geht über HTTPS, also greift der mitgelieferte CA-Speicher. Damit ist der eine Pfad gemessen, den es auf macOS gar nicht gibt. Nebenbei gelernt, für die nächste solche Messung: **auf einem usr-merged Debian ist `/bin` ein Symlink auf `/usr/bin`**, ein `PATH=/bin:/usr/sbin:/sbin` enthält git also weiterhin. Ein git-loses PATH baut man dort als Verzeichnis voller Symlinks auf `/usr/bin/*` ohne `git*`. Geschrieben werden sie erst, **nachdem** die Binärdatei geantwortet hat — eine halb gesetzte Umgebung würde auch ein später gefundenes Host-git verbiegen.
- **Host zuerst, und „Host" heißt: antwortet auf `git --version`.** Die umgekehrte Regel zu der für Node, aus dem umgekehrten Grund: git hat keine Versionsuntergrenze, trägt aber die Einrichtung des Nutzers — sein `~/.gitconfig` kann auf Helfer zeigen, die nur seine Installation hat (unser ausgedünntes Bundle bringt `git-credential-osxkeychain` nachweislich nicht mit). Die Prüfung durch Ausführen ist keine Zeremonie: auf einem macOS ohne Xcode-Werkzeuge liegt in `/usr/bin/git` ein Stub, der einen Installer öffnet — die Datei ist genau auf den Rechnern da, auf denen es kein git gibt.
- **Beim Packen geholt, nicht beim Installieren.** `beforePack` (`scripts/before-pack.mjs`) läuft je (Plattform, Architektur) — ein `dist` für arm64 *und* x64 packt zwei — und greift auch, wenn jemand `electron-builder` direkt aufruft. Es spiegelt das richtige Bundle nach `resources/git/current`, weil `extraResources` einen festen Pfad braucht und ein falsch geratenes `${arch}`-Makro erst als fehlendes git im fertigen Bundle auffiele. Beim Kopieren `dereference: false`: die 145 Symlinks aufzulösen bläht 26 MB auf über ein Gigabyte.
- **Gemessen mit einem PATH ohne git** (auf diesem Rechner liegt git nur in `/usr/bin`, nachgesehen): die App löst auf das Bundle 2.53.0 auf, die Startseite liest „Werkzeuge bereit · in der App: node 24.18.1, npm 11.17.0, git 2.53.0" ohne Warnband, `sync.status` liest Branch, Upstream und Änderungsliste des Testprojekts, und der ganze Einsteigerweg über die eigene IPC — Projekt anlegen mit Klon, `npm install`, Wizard und dem `git remote add upstream`, das die Quartz-CLI am Ende macht — läuft durch. Am gepackten Bundle: 30 MB in `Resources/git`, Symlinks intakt, `git clone` über HTTPS mit `env -i`.
- **Ein Werkzeug kann seit 7c nicht mehr „fehlen, aber nachinstallierbar" sein.** git zählt nur dann als das des Rechners, wenn es geantwortet hat — ein *kaputtes Host-Werkzeug* gibt es also nicht mehr, und der „installier dir git"-Hinweis im Warnband war unerreichbarer Code mit Übersetzung in zwei Dateien. Übrig bleibt ein Satz: wenn ein Werkzeug nicht läuft, ist die Installation unvollständig. Mit `process.env.PATH = '/nonexistent'` im Hauptprozess nachgestellt.
- **git ist GPLv2 und reist als eigenständiges Programm mit** — der Weg, den GitHub Desktop seit Jahren geht. `resources/licenses/git-LICENSE.txt` trägt den vollständigen Text, was entfernt wurde, wo der Quelltext liegt und ein schriftliches Angebot; die Einstellungen nennen die Lizenz und verlinken auf den Quelltext genau der mitgelieferten Fassung. Beim Anheben der Version sind das drei Stellen: `fetch-git.mjs`, die Lizenzdatei und `GIT_SOURCE_URL` in `Settings.tsx`.

**`npm run check:runtime -- <projekt>`** prüft diese Kette von außen, weil keiner ihrer Fehler im Typcheck oder im Build sichtbar wird — sie passieren alle in einem Kindprozess, derselbe Grund, aus dem `check:i18n` existiert. Zwei Prüfungen sind nach dem geformt, was sie *nicht* durchlassen dürfen: die Loader-Prüfung liest `process.defaultApp` direkt und fährt die Gegenprobe im selben Atemzug (mit `-r`: true, ohne: undefined), und die CLI-Prüfung ist `quartz plugin list` statt `--help`, weil Hilfe ihre Verwendung ausgibt, egal wie argv zugeschnitten war. Beim ersten Lauf hat das Skript sofort einen echten Fehler gefunden: `replace()` hatte den Platzhalter im Kommentar der eigenen Vorlage ersetzt und den Befehl mit einem literalen `__SCRIPT__` stehen lassen, der `node`-Shim der App war also kaputt. Beide Seiten benutzen jetzt `replaceAll`.

**Flatpak: konfiguriert, nicht gemessen (Phase 7b, 2026-09-03).** flatpak-builder läuft nur unter Linux; was in `electron-builder.yml` unter `flatpak:` steht, ist aus `app-builder-lib/out/targets/FlatpakTarget.js` und den BaseApp-Manifesten abgeleitet, und der erste echte Build gehört auf eine Linux-Maschine. Bis dahin ist der Abschnitt eine begründete Vermutung - anders als alles andere in dieser Datei. **Verschoben, nicht liegengeblieben:** der erste Bau gehört am 2026-09-03 auf Entscheidung hin in die Version nach v1, die genau die drei Ziele ausliefert, die gemessen sind - dmg/zip, AppImage und deb.
- **Erst mit der eingebetteten Laufzeit ist Flatpak überhaupt möglich.** In der Sandbox gibt es kein Host-Node, und `flatpak-spawn --host` bräuchte `--talk-name=org.freedesktop.Flatpak` - faktisch ein Sandbox-Ausbruch, um ein `npm install` zu starten. Phase 7a ist die Voraussetzung, nicht der Komfort.
- **git muss hier aus der Quelle gebaut werden, obwohl seit 7c eines mitreist.** Gemessen an den ELF-Kopfzeilen des Linux-Bundles: die Hauptbinärdatei braucht nur `libz` und `libc`, aber `git-remote-http` hängt an `libcurl-gnutls.so.4` - ein SONAME, den Debian und Ubuntu haben, die freedesktop-Runtime nicht (dort heißt sie `libcurl.so.4`, OpenSSL-Variante), Fedora und Arch auch nicht. Das Bundle bringt keine einzige Bibliothek mit (`find -name '*.so*'` ist leer). In der Sandbox käme es also bis `git --version` und stürbe beim ersten `clone`. Das Modul baut dieselbe Fassung (2.53.0) aus dem kernel.org-Tarball, mit `NO_GETTEXT` (wie das ausgedünnte Bundle), `NO_PERL` und `NO_PYTHON` (send-email, svn, p4 ruft diese App nie auf).
- **Derselbe Befund hat einen Wächter im Code erzwungen:** `gitRuntime.httpsHelperLoads()` startet `git-remote-https` ohne Argumente, bevor das Bundle akzeptiert wird. Der Helfer beschwert sich über die fehlende URL, *nachdem* der Loader fertig ist (Exit 1, gemessen); fehlt eine Bibliothek, kommt er nie so weit (Exit 127 plus Loader-Meldung). Ein Bundle, das daran scheitert, wird nicht benutzt - sonst hätte die App ein git, das jede Prüfung besteht und beim ersten Klon stirbt.
- **25.08 statt 24.08** für Runtime und BaseApp: der Zweig wird gepflegt (letzter Commit April 2026 gegen September 2024) und führt **libsecret** als SDK-Erweiterung, wo 24.08 noch libgnome-keyring hatte. `safeStorage` hängt unter Linux genau daran, und ohne Schlüsselbund landen Zugangsdaten praktisch im Klartext - deshalb steht `--talk-name=org.freedesktop.secrets` auch in den `finishArgs`. Weggelassen gegenüber electron-builders Vorgabe: `--socket=pulseaudio` und `--talk-name=org.freedesktop.Notifications`, weil diese App weder Ton ausgibt noch Systemmeldungen schickt.
- **`--filesystem=home` ist die bekannte Grenze.** Ein Content-Ordner ist oft ein Symlink in einen Obsidian-Vault; liegt der auf einem anderen Laufwerk, sieht die Sandbox ihn nicht, und es braucht ein `flatpak override --filesystem=…`. Ebenfalls bekannt und ungelöst: das 28-MB-git-Bundle aus 7c reist auch in den Flatpak mit, wo es nutzlos ist - `extraResources` gilt für alle Linux-Ziele.
- **Was beim ersten Linux-Build zu prüfen ist**, in dieser Reihenfolge: baut es überhaupt (Runtime, SDK und BaseApp 25.08 müssen installiert sein); startet die App unter zypak; findet sie das Modul-git (Einstellungen → Laufzeit muss „vom System" sagen, weil `/app/bin` im PATH liegt); legt sie ein Projekt an; meldet das Warnband den Schlüsselbund als sicher. Der größte Unbekannte ist zypak in Verbindung mit den Shims aus 7a: die App startet Kindprozesse, die dieselbe Electron-Binärdatei mit `ELECTRON_RUN_AS_NODE` aufrufen, und zypak hängt sich per LD_PRELOAD in Prozessstarts. Dass VS Code das im eigenen Flatpak seit Jahren so macht (sein Extension Host läuft genauso), ist ein Indiz - kein Beleg.
- **flatpak steht nicht in `linux.target`**, weil das Ziel flatpak und flatpak-builder auf der Baumaschine braucht und `npm run dist:linux` ohne die beiden nicht scheitern soll. `npm run dist:flatpak` baut es; `@malept/flatpak-bundler` liegt als Abhängigkeit von electron-builder schon bei (0.4.0).

**App identity ("QuartzControl")**: `app.setName('QuartzControl')` (called before `whenReady` in `electron/main/index.ts`) and `app.dock.setIcon()` (in `whenReady`, since `BrowserWindow`'s `icon` option has no effect on macOS's Dock) only change things `app.*` actually controls at runtime — they do **not** change the bold app name in the macOS menu bar, the Dock tile's name/icon shown from the moment the process launches, or (verified by hand) the Dock item's name even after editing `Info.plist` alone, because in dev all of that traces back to `node_modules/electron/dist/Electron.app` itself — its bundle folder name/path (which the Dock's name tracks, not just `CFBundleName`), its `Info.plist`, and its `electron.icns`, all read before any app JS runs. `scripts/brand-electron.mjs` (wired into `postinstall`) fixes this for the local, gitignored Electron copy: renames `Electron.app` → `QuartzControl.app`, rewrites `node_modules/electron/path.txt` to match (no trailing newline — `electron`'s `index.js` does `readFileSync(...).toString()` with no `.trim()`), sets `CFBundleName`/`CFBundleDisplayName`, swaps in `build/icon.icns`, and re-registers the bundle with `lsregister -f` so LaunchServices/Dock don't serve a stale cached entry for the old path. Idempotent, macOS-only; re-run it manually after a fresh `npm install` if the menu bar or Dock still say "Electron" (`node scripts/brand-electron.mjs`). `build/icon.png`/`build/icon.icns` are checked in, together with the exports they are built from. A packaged build needs none of this: `electron-builder.yml` sets `productName` and points at `build/icon.icns`, so the bundle is named correctly from the start — `brand-electron.mjs` exists purely so that *development* doesn't say "Electron".

**App icon**: the artwork is a drawn asset - a light gear on a blue-to-red gradient tile, its centre cut out as a circle with a diagonal bar running out through the lower right, so the two together read as a Q. `build/icon-source/` holds the versioned vector copy (`quartzcontrol-icon.svg`) and one PNG export per size; the Affinity document beside them is gitignored (`*.af`, 1.9 MB of binary that only the drawing needs), which makes the SVG the reference for what the icon *is*. `scripts/build-icon.mjs` (`npm run icon`) assembles: it checks every export's pixel size, copies the 512 to `build/icon.png`, the 256 to `build/icon-256.png` and to `src/assets/app-icon.png` (the start page's header image, which had once been a stale copy of the previous icon), and hands the ten Apple-named sizes to `iconutil` for `build/icon.icns` (macOS-only step; elsewhere the flat PNGs are still written).

**Every size is an export now, 16 and 32 included (2026-09-06).** They used to be *derived* here - a box average of the 1024 in linear light plus a 0.5 unsharp pass - because Affinity's own exports at those sizes read worse: averaging sRGB directly darkens every mixed pixel (at 16 px one output pixel covers 64x64 of the master), and the previous artwork's crystal sank into its gear as one grey blob. Two things had been tried on that glyph and had not worked: fusing its 17 facets into one silhouette removes the internal lines the crystal is recognised by, and thickening the separators reads as a broken crystal at 32 px. The note that closed the measurement said what would actually fix it - "a simplified glyph drawn in the vector document, not a better filter" - and the 2026-09-06 redraw is that: a single gear outline with one hole in it, which survives 16 px as a shape. With hand-drawn 16 and 32 in `build/icon-source/`, the 150 lines of PNG decoder, resampler and encoder that existed only for those two sizes are gone from the script; it copies, and that is all it does.

The tile is unchanged across the redraw - 824x824 at (97.4, 94.2) on the 1024 canvas, corner radius 125.3, Apple's ~10% margin with the tile sitting ~5 px above centre, which is below what any size renders. What changed with it is the gradient, from rgb(152,166,222)→rgb(233,167,172) to a deeper rgb(69,91,155)→rgb(221,120,127), and the vector itself: the old SVG was 98 kB because the glyph was an embedded bitmap inside it, the new one is 3.4 kB of paths. The first icon replaced a procedural generator (a violet crystal glyph with a hand-rolled rasterizer and PNG encoder) on 2026-09-03; the second replaced the first on 2026-09-06.

**Die eine Datei, deren Antwort ein Dialog ist (2026-09-05).** Auf einem macOS ohne
Xcode-Kommandozeilenwerkzeuge liegt in `/usr/bin/git` ein Shim, der statt zu antworten Apples
„Install Command Line Developer Tools“ öffnet. Der Kommentar in `gitRuntime.ts` wusste das, und
`probeVersion` führte die Datei trotzdem aus — aus `applyGitRuntime`, das vor `createWindow` läuft.
Auf genau den Rechnern, für die das mitgelieferte git existiert, wäre das erste, was die App tut,
Apples Installer gewesen, vor dem eigenen Fenster; `probe()` in `environmentService.ts` hätte ihn bei
jedem Mount der Startseite und der Einstellungen erneut geöffnet. `isCommandLineToolsStub()` stellt
dieselbe Frage ohne Nebenwirkung: `xcode-select -p` nennt das aktive Developer-Verzeichnis oder
endet mit einem Fehler. Gesperrt ist nur `/usr/bin/git` — ein git von Homebrew oder MacPorts ist eine
gewöhnliche Binärdatei —, und die Antwort wird nicht gecacht, damit eine nachträgliche Installation
ohne Neustart wirkt. Auch die drei „ist git erreichbar“-Prüfungen in `ensureToolPath()` gehen darüber,
sonst würde ein nur über die Login-Shell erreichbares git zugunsten eines Stubs übergangen. Gemessen
auf einem Rechner *mit* den Werkzeugen: `xcode-select -p` antwortet, an der Auflösung ändert sich
nichts, die App meldet weiter git 2.50.1 aus `/usr/bin/git`. Der andere Zweig ist nicht gemessen —
kein solcher Rechner verfügbar, und `DEVELOPER_DIR` kann ihn nicht nachstellen (`xcode-select -p`
gibt zurück, was man ihm vorsetzt, und endet mit 0).

**Die Fassung des mitgelieferten git steht an einer Stelle (2026-09-05).** Sie stand in
`scripts/fetch-git.mjs`, das die Binärdatei holt, und noch einmal in `Settings.tsx`, das auf den
Quelltext *dieser* Binärdatei verlinkt — jeweils mit einem Kommentar, der zum Nachziehen der anderen
Stelle aufforderte. Driftet eine, zeigt das schriftliche Quellcode-Angebot auf eine Version, die nie
ausgeliefert wurde, und ist damit keines. `shared/bundled-git.json` hält sie jetzt: das Skript liest
sie mit `readFileSync` (es ist reines Node und kann kein TypeScript importieren), der Renderer
importiert sie als JSON und baut den Link daraus.
