# Prozessmodell, IPC-Grenze und Main-Prozess-Hygiene

Aus CLAUDE.md ausgelagert (2026-09-02): die Messungen und Beobachtungen hinter den Regeln, wortgleich. Die Regeln selbst stehen in CLAUDE.md; hier steht, welches Experiment sie erzwungen hat. Neue Einträge kommen mit derselben Form dazu: was gemessen wurde, was daraus folgt.

**Three-process Electron split**, wired together by `electron.vite.config.ts` (main/preload/renderer each get an explicit `build.rollupOptions.input` since the source lives under `electron/main`, `electron/preload`, `src/` rather than electron-vite's default `src/main`/`src/preload` convention):

- `electron/main/` — Node-side logic. `index.ts` creates the window and installs a native macOS menu; `ipc/handlers.ts` wires every `ipcMain.handle` to a service and forwards service events (`server:log`, `build:log`, `server:statusChanged`, `content:progress`) to all renderer windows; `services/*.ts` each own one concern (`projectStore`, `configService`, `pluginService`, `pluginSchemaService`, `marketplaceService`, `buildService`, `runningServersStore`, `syncService`, `backupService`, `contentService`, `createService`, `settingsService`, `connectionsService`, `publishTargetsService`, `deploy/` (dispatcher + one adapter per destination type), `gitStatusService`, `githubPagesService`, `styleService`, `variableGraphService`, `updateService`, `layoutFrameService`, `templatePackageService`, `themePresetsService`, `themeMarketplaceService`, `styleSettingsSchemaService`, `fontService`, `localizationService`, `environmentService`, `projectDirs`, `runCommand`) and are plain functions with no Electron-API dependencies beyond `app.getPath`/`dialog`, which keeps them runnable standalone.
- `electron/preload/index.ts` — the only file allowed to import both `electron` and the app's shared types; implements `QuartzGuiApi` via `contextBridge.exposeInMainWorld('quartzGui', ...)`.
- `shared/ipc-contract.ts` — the single source of truth: every IPC channel name (`IPC.*` const), every payload/domain type (`Project`, `QuartzConfig`, `PluginEntry`, `ServerStatus`, ...), and the full `QuartzGuiApi` interface that preload implements and the renderer calls as `window.quartzGui.*`. Change a channel or a type here first; main and preload/renderer follow.
- `src/` — the renderer (React Router `HashRouter`). `App.tsx` declares routes; `routes/ProjectLayout.tsx` is the per-project shell (sidebar nav + drag region) and passes the current `Project` down via `Outlet context`, read in child routes with `useProject()`. `state/store.ts` (zustand) holds cross-page state (project list, settings) — everything else (config being edited, server status) is local `useState` in the page that owns it, fetched via `window.quartzGui.*` on mount and via the `onStatus`/`onProgress` subscriptions for live updates. `components/ui.tsx` has the shared primitives (`Button`, `Card`, `Field`, `TextInput`, `Select`, `Toggle`, `SegmentedControl`, `Badge`, `PageHeader`) — extend these rather than hand-rolling styled elements.

**No `window.quartzGui.*` call is left unguarded.** Two layers, because they fix different halves: `ErrorSurface.installGlobalErrorHandlers()` catches every unhandled rejection into an app-wide toast (so a failure is always *visible*, including on the mount-time loads no page wraps), and each handler that sets a busy flag resets it in a `finally` (so the page stays *usable*). Without the second half a rejected invoke left the button disabled on "Speichere…" for good — reproduced in the running app before it was fixed. Use `useAsyncAction()` for a boolean pending flag; a plain `try/finally` where the flag is keyed (which direction is syncing, which plugin is installing), since the hook's boolean doesn't fit those. `formatIpcError()` unwraps Electron's `Error invoking remote method '<channel>':` nesting and keeps the channel name.

**The app window never leaves the app's own document, and the renderer never opens a socket.** `setWindowOpenHandler` covers `window.open` and `target="_blank"`; a navigation of the window *itself* - a link with no target, anything assigning `location.href` - was unguarded, and this is the window carrying the preload bridge. Measured against the packaged build through the run-desktop driver: `location.href = "https://example.com/probe"` loaded that page into the app window, where `typeof window.quartzGui.projects.list` read `"function"` - every IPC channel reachable from a remote origin. The `will-navigate` handler in `createWindow` allows exactly the document this window was loaded with (in the packaged case decided on the *path*, because a `file:` URL's origin is opaque - `"null"` in Chromium - and comparing origins would have allowed any local file) and hands http(s) to the browser like an external link. Hash changes and reloads do not fire it, so the HashRouter and dev-mode HMR are untouched. The CSP goes with it: the renderer makes no network request of its own - every `fetch` in this app is in main, which is also where the GitHub token lives - so `connect-src 'self'` (which still covers Vite's HMR websocket, verified) and `img-src 'self' data:` with no remote host, plus the three directives `default-src` does not cover (`object-src`/`base-uri`/`form-action` `'none'`). `about:` slips past `will-navigate` in Chromium; it leaves a blank window and no attacker content, and getting there already requires script execution in the renderer.

**Every small JSON store goes through `services/jsonStore.ts`, and a store that cannot be read is never overwritten.** They all used to `writeFile(JSON.stringify(...))` and read back with `try { JSON.parse } catch { return [] }` - two halves that fail in the same direction and together delete data, since writeFile truncates before it streams and the empty default is then committed over the damage. `connections.json` did not even defer it: `readAll()` treated any parse failure as "no store yet", ran the legacy migration and wrote the result back - measured, one truncated file became `[]` on a single `listConnections()` call, taking every stored password, key, webhook URL and the GitHub token with it. Writing is now temp-file + `fsync` + `rename` (atomic within a directory; 40 concurrent writes leave a valid file and no leftovers), and reading distinguishes `missing` (the normal first run) from `unreadable` - the latter moves the file aside as `<name>.corrupt-<time>`, records it for `AppInfo.unreadableStores`, and Settings' maintenance section says so. A bare `null` or an object where a list belongs counts as unreadable too: `JSON.parse` accepts both and every caller treated them as data. A frame's `frame.json` gets the atomic write but *not* the quarantine - moving it aside would take apart a directory `quartz.config.yaml` still points at.

**Everything that leaves this machine has a deadline, and a spawn that collects output resolves on `close`.** Node's `fetch` falls back to undici's 300s, `npm search` and `git ls-remote` have none at all - so a stalled connection (as opposed to a failed one) left the Marktplatz, the Themes tab and the Updates tab spinning with no cancel. `runCommand` takes an optional `timeoutMs` (used for `ls-remote`, which four of run unprompted on opening Updates) and answers it *itself* rather than waiting for the kill's `close`, since a child that left a grandchild holding stdout keeps the pipe open past its own death. That is also why `close` replaced `exit` wherever output is collected: measured, a child leaving a grandchild on stdout showed `"HEAD"` at `exit` and `"HEAD\nTAIL"` at `close`, while a plain fast-exiting child drains first (30 runs at 4 MB, not a byte missing). Only in rsync's preview does the difference show as *wrong* output rather than late output - the itemized lines are the result there, and rsync's own ssh child holds stdout open.

**A path list goes into argv, and argv has a ceiling.** `git checkout <commit> -- <paths…>` with a whole selection: measured against real git on macOS (ARG_MAX 1048576), 16000 paths / 834 KB spawn and 18000 / 940 KB do not - and `spawn()` throws E2BIG *synchronously*, so `runCommand`'s `error` listener never sees it and the restore ends as a bare "spawn E2BIG" having done nothing. The snapshot restore batches its selection in thousands; the whole-project restore is one `read-tree` and passes no paths at all. Same reasoning applies to any future call that forwards a user-sized list.

**A catalog fetch is coalesced, and searching it does not touch the network.** The Marktplatz ran `marketplace.search(query)` from an effect keyed on the query - one IPC round trip per character, and because a failed catalog fetch is deliberately never cached, one *GitHub request* per character whenever the API was unreachable, with no ordering guarantee between the answers. The channel is `marketplace.list()` and returns the catalog whole; the ~60 repositories are filtered in the renderer's existing `useMemo`. Both catalog services also share an in-flight fetch, since StrictMode's double mount otherwise fired two full ones per visit (for themes: two `npm search` processes plus two rounds of GitHub pagination).

**The deploy manifest streams.** `buildCurrentManifest` read every file a build emitted into memory *and* did so in one `Promise.all` over the whole list, so peak memory in the main process was the size of the site: measured over 6000 files of 60 KB, +448 MB RSS at once against +109 MB streaming 32 at a time (309 ms vs 442 ms). Digests are identical, checked file by file against the plain readFile hash over a real build.

**Every IPC handler declares a zod schema for its arguments — adding a channel without one is the bug.** `electron/main/ipc/handle.ts` wraps `ipcMain.handle`; `schemas.ts` holds the shared primitives (`absolutePath`, `relativeSubPath`, `backupId`, `snapshotTag`, `pluginName`, `frameId`, `localeCode`, `branchName`, …). The renderer is not a trust boundary: contextIsolation only keeps *our* preload honest, and the Marketplace and Styles→Theme tabs render data fetched from GitHub, so anything reaching a service can spawn processes and write/delete files at arbitrary paths. Validation failure throws — the handler never runs — and logs the channel plus the offending argument.
- **Schemas here are deliberately looser than the contract types**, using `z.looseObject`/`z.record`: `z.object()` *strips unknown keys*, which would silently drop a plugin entry's `layout` field on the next save and break the round-trip `configService` protects. That looseness is why the payload handlers carry a documented `as <ContractType>` cast — the alternative, a precise zod mirror of `ipc-contract.ts`, would be a second source of truth that drifts.
- **A `.refine` must not assume the checks before it passed.** zod v4 keeps running a schema's remaining checks after one fails, so a refine also sees the values its own `.regex()` just rejected — `styleFileSubPath`'s `p.split('/')[1].startsWith('.')` threw a `TypeError` for `custom.scss`, which reached the renderer as a crash instead of the readable "kein gültiger Stylesheet-Pfad". A type mismatch does abort (a refine never sees a number where it expects a string), same-type failures do not.
- **A target's remote path may be relative, and the rule lives in `shared/remotePath.ts`.** It used to require a leading slash, which is wrong twice over: every consumer joins it with `posix.join` (sftp, ftp) or appends it to `user@host:` (rsync), all of which resolve a relative path against the login's own directory - the normal way to address a shared webspace, whose absolute equivalent the provider's panel often does not even show. And the refusal arrived at the IPC boundary, where a rejected argument is reported as *a bug in the app rather than something you typed* - true everywhere except this one field, which a user fills in freely. Measured: entering `httpdocs` produced `arg[1.destination.remotePath]: must be an absolute path`. The rule is shared with the target form (the `rsyncSupport` precedent) so the form can never offer a value the boundary refuses; what is still refused is nothing at all, the login's own root (`/`, `.`, `./` - a deploy with deletion enabled would empty it) and any `..` segment, each with its own sentence at the field. A fresh draft no longer starts on `/` either, which was a default the boundary rejected.
- An **output directory may be relative *or* absolute** (`s.buildOutputDir`): BuildServer's one-off export picks a folder from the native dialog, which always yields an absolute path. `projectDirs.resolveBuildDir()` is the single interpreter — a plain `join()` would mis-resolve an absolute one (`join('/projekt', '/export') === '/projekt/export'`). `deploy/index.ts` and `styleService` go through it; `githubPagesService` is the one place that still doesn't.
- Two rules can't live in a schema and sit in code instead: `dialogOpenPath` resolves the path and refuses anything outside a **registered project directory** (`shell.openPath` launches `.app` bundles), and `githubPagesService` refuses a deploy onto the checked-out or default branch (only it can resolve what those are).

**One helper spawns short-lived commands, and `git` never gets a shell.** `services/runCommand.ts` replaced four byte-identical `run()` copies; `buildService` and `themeMarketplaceService.fetchFromNpm` keep their own spawn (they stream / ignore stderr) but take the shell decision from the same `needsShell()`. That decision is *not* a blanket `shell: process.platform === 'win32'`: a shell re-interprets metacharacters in the **arguments**, so a project path or output directory containing `&` would both break and become injectable. Only npm/npx need one (they're `.cmd` shims `CreateProcess` can't execute); `git` is a real `.exe`.
- **Arguments read from project files must be separated with `--`.** `updateService.lsRemoteHead` passes `git ls-remote -- <url> <ref>` because both come out of `quartz.lock.json`. Verified against real git: without the separator, `--upload-pack=<cmd>` **executes `<cmd>`**; with it, git refuses it as a "strange pathname". `getPluginsUpdateStatus` runs this for every lockfile entry just from opening the Updates tab.
- Same reasoning made `looksLikeQuartzServer` use `execFileSync('ps', [...])` instead of `execSync` with an interpolated pid — that pid is read back from a JSON file in `userData`.

**Orphaned dev-server detection asks, never auto-kills.** `buildService.startServer()` persists `{pid, port, startedAt}` per project via `runningServersStore` (a JSON file in Electron's `userData`) and clears it on the process's `exit` event — but a non-graceful app exit (crash, force-quit) skips that cleanup, and a *graceful* quit's `before-quit` handler kills tracked servers itself, so the persisted file should normally be empty on the next launch. When it isn't, `index.ts`'s `promptForOrphanedServers()` (before `createWindow()` in `whenReady`) calls `detectOrphanedServers()` — which checks the PID is actually alive *and* sanity-checks its command line (`ps -p <pid> -o command=`) before trusting a stored PID — and shows a native confirm dialog rather than silently killing: the server might have been started outside the app on purpose, so only an explicit "Beenden" click calls `killOrphanedServers()`.

**`sandbox: false` was never a decision, and the sandbox is on now (2026-09-02).** electron-vite emitted the preload as `index.mjs` because the package is `"type": "module"`, and Electron loads an ESM preload only into an unsandboxed renderer (`tutorial/esm.md`: "Sandboxed preload scripts are run as plain JavaScript without an ESM context"). That single constraint is what put `sandbox: false` into `createWindow` - while `ipc/schemas.ts` argued all along that the renderer is not a trust boundary, which is only half true without the Chromium sandbox: a renderer bug would have had full Node through the preload context. The preload is built as CommonJS now (`preload.build.rollupOptions.output.format: 'cjs'`; with `rollupOptions.input` set, electron-vite honours a user `output.format` and only applies its `.mjs` renaming to `format: 'es'`, read in `node_modules/electron-vite/dist/chunks/lib-*.js`), and the one Node call it had - `os.homedir()` for `api.homeDir` - is replaced by `--quartz-home-dir=<path>` in `webPreferences.additionalArguments`, read back from `process.argv`. That is preferred over `ipcRenderer.sendSync` because the value is needed synchronously at the first render (`titlebarStripClass`, `expandHome`) and a sync round trip would sit in every preload start for one constant string; `process.platform` and `process.argv` are both on Electron's process polyfill for sandboxed preloads (`createPreloadProcessObject` plus the C++ bindings, checked in the Electron source). Verified against the production build through Playwright: `webContents.getLastWebPreferences()` reports `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`; `require` and `process` are `undefined` in the page; `platform` and `homeDir` carry the right values; the macOS strip renders `titlebar-drag h-12 shrink-0` on the first paint; the Settings default-directory field still expands `~/Documents`.

**Yes/no questions are native, in-app overlays are for forms and selections (2026-09-02).** The renderer used `window.confirm()` at 18 sites, most of them before something destructive (deploy, snapshot delete/restore, plugin remove, project remove). That dialog's default button belongs to Chromium and Return confirms it - the exact failure the build guard measured in main, where Return took `buttons[0]` regardless of `defaultId`. `dialog.confirm` (`ConfirmDialogOptions`, one object argument, `looseObject` schema) puts Cancel in `buttons[0]` with `cancelId: 0`, attaches the dialog to the window so it is a sheet, uses `type: 'warning'` for anything destructive and takes its Cancel label from `mainT('confirmCancel')` so it follows the language setting. `src/utils/confirm.ts` splits the existing texts at their blank line into `message`/`detail`, so no text was rewritten; each site names its action on the confirming button. The sidebar's leave guard became asynchronous: `preventDefault()` first, `navigate(to)` once "discard" came back - `to` resolved relative to the layout route the same way the NavLink does (`item.to || '.'`, `'/'` for the project list). Verified with `dialog.showMessageBox` spied in main through Playwright's `app.evaluate`: `["Abbrechen", <action>]`, `defaultId 0`, `cancelId 0`, `warning`, attached to a `BrowserWindow`, `["Cancel", …]` after switching the language to English, `false` for response 0 and `true` for 1; the guard stays on the page for 0 and lands on `plugins` resp. `#/` for 1. Not measured: the OS's own Return handling (osascript has no accessibility permission on this machine) - it rests on the build-guard measurement.

**`Modal` is the native `<dialog>` (2026-09-02).** The two hand-rolled overlays (create wizard, content-source change) were `fixed inset-0` divs: no role, no Escape, no focus trap, no focus return, Tab walked through the page behind them. `showModal()` gives the top layer, `::backdrop`, Escape via the `cancel` event, an inert document and focus back to the opener on `close()`; `<form method="dialog">` makes Return submit, and a disabled submit button suppresses implicit submission. Three things had to be learnt on the way: React's `autoFocus` calls `.focus()` at mount while the dialog is still `display:none`, so the target field carries `data-autofocus` and is focused after `showModal()`; an open dialog that is merely removed from the DOM is not closed, so focus lands on `<body>` - the cleanup calls `close()`, and it has to be a `useLayoutEffect` cleanup because React runs those before it removes the host node and passive ones after; and StrictMode's simulated unmount in dev fires that cleanup, whose `close` event would have reached `onClose` and unmounted the wizard for real, hence the `closingOurselves` ref. `Button` defaults to `type="button"` since then: inside that form an untyped Cancel or "Ordner wählen" would have confirmed the dialog, and outside a form the attribute changes nothing for the 125 existing sites. Verified in the production build: initial focus on the named field, Tab confined for twelve presses, an outside button refusing programmatic focus, Escape and Cancel returning focus to the opening button (only when the opener had focus - a DOM `.click()` in a test leaves nothing to return to), Return with an empty name doing nothing, Return with a bogus source folder submitting and showing the service's refusal inside the dialog.
