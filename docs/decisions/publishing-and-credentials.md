# Veröffentlichen: Zugänge, Ziele, Adapter, Git-Sync und Zugangsdaten

Aus CLAUDE.md ausgelagert (2026-09-02): die Messungen und Beobachtungen hinter den Regeln, wortgleich. Die Regeln selbst stehen in CLAUDE.md; hier steht, welches Experiment sie erzwungen hat. Neue Einträge kommen mit derselben Form dazu: was gemessen wurde, was daraus folgt.

**The handshake budget has to cover a human reading a fingerprint.** ssh2's `readyTimeout` (20s by default) runs across the *whole* handshake, and `hostVerifier` opens a native dialog in the middle of it asking the user to compare a SHA256 fingerprint against what their provider publishes - which is a task measured in minutes. Reported from a real SFTP connection: the first attempt died with "Timed out while waiting for handshake" and the second succeeded, the second having no dialog because the key had been pinned by then. ssh2 offers no way to pause the clock, so `sftp.ts` widens `readyTimeout` for exactly the connection that will ask (no pinned fingerprint) and leaves the default in place afterwards, where a long wait really does mean an unreachable host. A deploy is also where a pin gets written, so `Publish` re-reads the connections when one finishes - the card otherwise still read "Host-Key noch nicht bestätigt" until the page was left and re-entered.

**SFTP host keys are pinned (trust on first use), and the pin belongs to the host.** Without a `hostVerifier`, ssh2 accepts *any* host key — verified in its own source (`lib/protocol/kex.js`: "Host accepted by default (no verification)"), which makes the connection trivially interceptable. `services/deploy/hostVerifier.ts` therefore passes one: the first connection shows the server's `SHA256:…` fingerprint in a native dialog and, on confirmation, pins it onto the **connection** (`connectionsService.rememberHostKey`), not onto a per-project profile — the same server reached from two projects must not end up with two pins that can drift apart, which is the exact failure trust-on-first-use exists to prevent. A later **mismatch is refused outright, with no "continue anyway" option** — that dialog is exactly where users click through, and a changed key is indistinguishable here from an interception. The way back is the explicit "Host-Key vergessen" button (`connections.forgetHostKey`). `fingerprintOf()` reproduces OpenSSH's format exactly (verified against `ssh-keygen -lf` for ed25519/RSA/ECDSA), so the string can be compared 1:1 with what a provider publishes.
- **The raw key blob is stored alongside the fingerprint, and that is not redundancy.** A fingerprint is a hash, so ssh(1) cannot be pinned with it — a `known_hosts` line needs the actual key. rsync (planned) shells out to ssh, so without the blob it would need its own separate trust store. `keyTypeOf()` reads the algorithm out of the blob itself (RFC 4253 §6.6: a length-prefixed algorithm name comes first) rather than guessing it from the connection. A pin migrated from the pre-split store has a fingerprint but no blob; it is backfilled on the next connection that matches the trusted fingerprint.
- FTP has no equivalent — it's plaintext by nature; `secure: true` (FTPS) is the only protection there.

**A target's `excludes` are applied in the dispatcher, not in the adapters.** They are the paths one target never publishes, kept between runs - as opposed to the checkboxes in the diff, which skip one deploy. `deploy/index.ts` filters them out of `previewDeploy`'s result and unions them into `runDeploy`'s exclusions, so preview and run cannot disagree about what is invisible; a `git-branch` target is left out, because there leaving a file out of the one root commit *deletes* it from the live site. Before this the field was stored, migrated and documented but read by nothing at all. The same function is where a missing build is caught: every file adapter walks the output directory, and on a never-built project that used to surface as a raw `ENOENT ... scandir '<dir>'` from inside the manifest walk.

**Connections are app-level, publish targets are project-level.** A *connection* is what you have with a provider (an SSH login, an FTP account, the GitHub token, a webhook URL); a *target* is what one project does with it (remote path, branch, deletion behaviour, excludes). Three things forced the split out of the old per-project `DeployConnectionProfile`: a host key belongs to the host (above), one webspace commonly carries several sites with the same login and different paths, and rotating a password has to be one edit rather than one per project. `connectionsService.ts` owns the former in `userData/connections.json`; `publishTargetsService.ts` owns the latter in `<project>/.quartz-gui/publish-targets.json`, where it travels with the project and carries no secret at all.
- **Migration runs on first read and is staged on disk, not in memory.** `connectionsService.migrate()` splits each old profile into a connection (keeping the profile's id, so the remembered selection survives) plus a target, and pulls the GitHub token out of `settings.json`. The targets span every project the old file knew about and are claimed one project at a time — whenever that project is next opened, possibly several restarts later — so they go to `userData/legacy-publish-targets.json` and `publishTargetsService.listTargets` claims its own. An in-memory hand-off would drop every project but the first one opened after the migration. Verified end-to-end against synthetic legacy data: two profiles across two projects, both claimed, idempotent on a second run, `deploy-secrets.json` renamed to `.migrated` rather than deleted.
- **The deploy manifest is per target *and* expires when that target is re-pointed.** (`deploy-manifest-<targetId>.json`.) The shared per-project file it replaced meant that after deploying to A the manifest already matched the current build, so the diff for B came back empty and B silently received nothing — reproduced directly. The single legacy manifest is adopted by whichever target asks first (and renamed in the process), so the second target starts from a full upload rather than inheriting someone else's state. Per target is still not enough on its own: the manifest records what was last sent *to a place*, so changing a target's remote path or its connection makes every entry a claim about a different directory or a different machine - reported from a real deploy, where a changed remote path still produced a two-file diff into an empty folder. `saveTarget` compares a `locationKey` (connection id, destination type, remote path / folder path / branch) and drops the manifest when it moved; the transfer mode, the name and the exclusions are deliberately not part of it, since rsync and sftp reach the same directory and the other two change nothing on the far end. Everything the app *cannot* detect - a file deleted on the server by hand, an interrupted transfer, a restore from the provider's own backup - gets the explicit `deploy.forgetManifest` channel and an "Alles neu hochladen" button next to the diff. It is not a "deploy everything" action: it throws the record away and re-reads the diff, which then offers the whole build with the usual per-file checkboxes. Absent for a git-branch target, which compares trees on the remote and keeps no manifest at all.
- **`preview` is per adapter, not one shared diff.** The adapters disagree on what a diff is: sftp/ftp/folder compare the build output against the local manifest, rsync asks the remote itself via `--dry-run --itemize-changes` and needs no manifest, and a webhook has nothing to compare. Flattening those into one function is what forced the old code to treat every destination as a file transfer.
- **A removal that didn't happen must stay in the manifest.** There are two reasons a file can appear as `removed` and not be deleted: the user unticked it, or the target has `deleteRemoved` off. `commitManifest` only ever knew about the first, so with deletion disabled a file that vanished locally dropped out of the manifest as though it *had* been deleted remotely — it is still on the server, and no later run would offer to remove it, not even after switching deletion back on. `partitionDiff` therefore returns a third list, `manifestExcludes`, and every file adapter commits with that rather than the raw exclusions. Reproduced against real files before the fix, and re-verified after: deploy → delete locally with deletion off → nothing happens → switch deletion on → the file is still known and gets removed.
- **A folder target is not "build into that folder".** BuildServer's output-directory field points `quartz build` at a directory; a folder target copies a *finished* build there with the diff, the exclusions and the deletion of files no longer produced. Building straight into a synced folder writes progressively, so the sync client uploads a half-finished site, and nothing stops the build from clobbering whatever else lives there. `folder.ts` writes each file under a scratch name and renames it into place for the same reason — a rename inside one directory is not observable half-written, a copy is. It refuses both containment directions (target inside the build dir, build dir inside the target) via `relative()`, not `startsWith()`, which would call `/tmp/site-old` a child of `/tmp/site`.
**`quartz sync` commits, force-pushes, and always pulls `v5` - the page says so now.** All three defaults were read from the CLI's own `args.js` (`commit`, `push`, `pull` all default to **true**) and measured: `--no-push --no-pull` produced a 10-file commit under "Quartz sync: <date>", so even the "Pull" button committed the whole working tree. `SyncOptions` carries `commit`/`message`, the card has a toggle and a message field, and the explainer states the force push (`git push -uf origin <current branch>`) and the fixed pull target (`gitPull(ORIGIN_NAME, QUARTZ_SOURCE_BRANCH)`, i.e. `origin v5` whatever is checked out - a branch other than v5 gets a warning). A conflicted pull leaves a half-finished merge, and the way out was a terminal; the banner now offers `updates.abortCoreMerge`, which is a plain `git merge --abort` with the content symlink parked and only *named* after the core update.
  - **The push got no credential from this app at all.** Measured: without a credential helper for github.com, git answers "could not read Username for 'https://github.com': Device not configured" (it fails fast rather than hanging, since there is no tty) - while the branch deploy, which uses `gitAuthForOrigin`, worked. `runSync` passes the same env; verified that `GIT_ASKPASS` survives the npx → quartz → git chain, where the token reaches GitHub and it answers "Invalid username or token" instead.

**The GitHub API does the two things a branch push cannot.** `githubService.ts` covers creating a repository (`POST /user/repos`, then `git remote add origin`) and configuring Pages (`POST`/`PUT /repos/{o}/{r}/pages`) - the endpoints and payloads were read from the current docs, not from memory. Repo creation lives on **Git-Sync** (it is about the repository) and Pages configuration on **Veröffentlichen** under a GitHub branch target (it is about publishing), which is the sidebar's "a page is a job" rule applied.
- **Pages needs a public repository on a free account, and that is decided one page earlier.** GitHub answers `422: Your current plan does not support GitHub Pages for this repository` - measured against a real account - and that arrives on Veröffentlichen, after the repository already exists, from a decision made by a toggle on Git-Sync. The toggle carries the consequence as its hint; the API's own message is still passed through verbatim, which is what made the cause readable at all.
- **Enforcing HTTPS is a choice only a custom domain has.** A `*.github.io` site is served over HTTPS unconditionally and GitHub reports `https_enforced` as already true, so the switch was offering a decision that does not exist - and turning it off would have looked like it did something. It follows the domain field beside it rather than the stored value, since the domain being typed is the one this save applies.
- **`https_enforced` is sent as a second request on purpose.** GitHub can only enforce HTTPS once it has issued a certificate for the domain, which takes minutes after the CNAME is set - sending both in one PUT makes the whole call fail and the domain not get set either. The second call is allowed to fail with an explanatory message rather than failing the whole action.
- **GitHub turns Pages on by itself once a public repository has a `gh-pages` branch**, so the card can find Pages already configured without this app ever having asked for it - observed during the alpha test, right after a repository was switched from private to public. That is also why the apply button is not a one-time setup action: once Pages already reads this branch it only saves the domain and HTTPS settings, and it says so instead of offering to point Pages at a branch it is already on. The published URL is a link, not printed text - the one moment a user wants to look at the result had no way to get there.
- **Setting the domain through the API is what makes a custom domain survive a deploy.** The branch adapter replaces the branch wholesale with one root commit, so a hand-committed CNAME file does not survive it; a domain set here is stored by GitHub itself and does.
- **A missing token is not thrown, it is a 401 from `api()`.** `getPagesInfo` runs on mount whenever a GitHub branch target is selected, and a user who has not entered a token would otherwise get an exception thrown at them for a card they were only looking at. The explicit actions report it as a failed result, which is where that message belongs. `pagesInfo` answering `null` (origin is not github.com at all) is a third state and renders as its own message, not as a form that could only fail.
- **`parseGithubRemote` matches `github.com` exactly, not by suffix.** A `/(^|\.)github\.com$/` test let `https://api.github.com/repos/x/y` through as owner `repos`, repo `x` - which would then be pasted straight into an API path. The scp-like form (`git@github.com:owner/repo`) is handled separately because it is not a URL and `new URL()` cannot parse it.

**A git credential reaches git only through `GIT_ASKPASS`.** `gitAuth.ts` writes a tiny helper script into a temp dir and passes the token in that one call's environment. Not in the remote URL - git writes that into the project's own `.git/config` and prints it from `git remote -v`, so the token would sit on disk inside the user's repo - and not in argv (`-c http.extraHeader=…`), which is visible in `ps`. `GIT_TERMINAL_PROMPT=0` goes with it, or a git that cannot use the helper falls back to prompting on the closed stdin every spawn here uses and hangs forever. It is handed out **only for an https remote on github.com**: an ssh remote authenticates with a key, and any other host was never issued this credential. Verified: the helper answers `x-access-token` to a username prompt and the token to a password prompt, the temp dir is removed afterwards, and a GitLab remote, an ssh remote and a project with no origin all get an empty environment.

- **A branch push is one adapter for three providers, and GitHub Pages is no longer a special case.** `deploy/gitBranch.ts` replaced `githubPagesService`: GitHub Pages (gh-pages), Codeberg Pages (a branch literally named `pages`, served directly) and GitLab Pages differ in the branch name and in what the provider does afterwards, not in the mechanism. GitLab is the honest exception - the branch alone publishes nothing there, a CI job has to ship the files, which the form says rather than the code pretending otherwise. The pseudo-target that bypassed the target list is gone (`deploy:githubPagesRun` with it): it was the last place this page reached past its own model, and `publish.githubBranch`'s sticky state went with it.
  - **It now has a real preview.** The branch is fetched, the build staged into the worktree and the written tree compared against the remote one (`git diff --name-status <remoteTip>^{tree} <newTree>`), so the diff is against what is *actually published* - GitHub Pages previously had no diff at all and its deploy button was ungated. Costs a fetch and a staging pass, hence on demand only.
  - **`excludePaths` is deliberately ignored here.** The branch is replaced wholesale by one root commit, so unticking a file would delete it from the live site rather than leave it untouched - the UI renders the diff read-only for this target type instead of offering checkboxes that would mean the opposite of what they say everywhere else.
  - The worktree path carries the target id, so two branch targets (live and staging) cannot fight over one registration, and `git worktree prune` runs first to clear registrations left by the single shared path this used before targets existed. Verified against a real bare repo: root commit with no parent, force-with-lease over an existing branch leaving exactly one commit, an unchanged build skipping the push, a real added/changed/removed preview, the protected-branch refusal, and no worktree left behind.

- **rsync is a transfer mode of an SFTP target, not a target type of its own** - same server, same remote path, reached a faster way - so it is a field on the `sftp` destination and `deploy/index.ts` resolves it. It keeps **no manifest**: `--dry-run --itemize-changes` asks the remote what is actually there, which is a strictly better diff and the one case that notices a file someone deleted on the server behind this app's back. Every flag was checked against **openrsync** (macOS ships protocol 29, "rsync 2.6.9 compatible", not rsync 3.x): `-rlt --delete --dry-run --itemize-changes --exclude-from -e --port` all exist; `--protect-args` does not, which is why a remote path containing whitespace is refused instead of quoted. `-rlt` rather than `-a` deliberately: `-a` also pushes this machine's permissions, owner and group onto the live site.
  - **`-e` is split on whitespace by rsync itself**, and both paths that belong in it routinely contain one — Electron's userData lives under "Application Support", and a key file can sit anywhere. So `-e` gets a wrapper script written into `mkdtemp(tmpdir())` (no spaces on macOS: `/var/folders/…`) with the paths quoted *inside* the script, where the shell does the parsing.
  - **`-o BatchMode=yes` means a passphrase-protected key only works through the agent.** The wrapper sets it so that no prompt can hang behind a pipe nobody reads, which also rules out ssh asking for a passphrase - so a `privateKey` + `keyPath` connection needs a key without one, while an agent connection can hold an encrypted key because the agent has already decrypted it. Worth saying out loud when anyone is set up for rsync.
  - **The rule for "can this connection do rsync" lives in `shared/rsyncSupport.ts`** and returns a machine-readable reason, not a message: main refuses on it and the target form uses it to decide whether to offer rsync at all. Two copies would drift and the UI would offer a transfer the adapter then rejects. It takes the platform as an *argument* rather than reading it — the renderer has no `process`, and `'platform-unsupported'` (Windows, where there is neither an rsync to spawn nor a shell for the `-e` wrapper) has to be answerable on both sides. The wording stays local on both sides (plain strings in main, i18n in the renderer). The three reasons: password auth (ssh cannot take a password from us and sshpass is not shippable), a key that exists only as stored text (ssh needs a *file*), and no pinned host-key blob (a `known_hosts` line cannot be built from a fingerprint) — the last one sends the user through one SFTP deploy, where the existing dialog shows the fingerprint properly.
  - **ssh's own failure text is not shown as-is.** Its host-key warning is a wall of `@` that ends by telling the user to edit a `known_hosts` file which is a throwaway in `/var/folders` and is deleted a moment later. A mismatch and a rejected key are translated to the same wording the SFTP path uses; anything else is passed through verbatim. Verified end to end against a real sshd on a high port: transfer, deletion, per-file progress, an honoured exclusion, and refusal on a wrong host key, a wrong user, password auth, a text-only key, an unpinned host and a remote path with a space.

- **A webhook is a credential in URL form.** A build hook's path *is* its token, so `webhook.ts` treats the URL like a password: stored encrypted, never sent to the renderer, and only its `origin` is ever printed — including in the deploy output. https is enforced twice, once in `saveConnectionInput`'s refine and once at the point the request actually goes out. **Printing only the origin is not enough, because the provider echoes the rest back**: webhook.site answers an unconfigured hook with `Change response in <a href="https://webhook.site/#!/edit/<id>">`, and that `<id>` is the same token as the hook URL's own path in a *different* URL shape - so searching the response for the secret string as a whole finds nothing. `redact()` therefore blanks the credential's individual parts (path segments, query values, fragment, userinfo, each at least 8 characters so ordinary words like "hooks" survive) out of both the response body and the error text, using split/join rather than a regex so a stored credential never has to be escaped. Found in the alpha test, on the one check T3 asks for by name. A webhook also gets its **own** deploy confirmation: the shared wording counts a diff this target does not have and read "0 Dateien werden hochgeladen, 0 Dateien werden gelöscht", which describes the action as doing nothing. Verified end to end against a local HTTPS server: 201 → success with the body truncated to 2000 chars, 404 → failure carrying the provider's message, http/missing/malformed refused, and the token segment absent from every output line.
- **"No credential stored" is not the same as `!hasSecret`.** A private key given as a *file path* deliberately stores no secret - the file is the source of truth, so a key that is moved or replaced needs no re-save - and both connection lists read `!hasSecret` directly. The result was an amber "kein Passwort/Key" hung on exactly the setup rsync requires, right after configuring one. `connectionMissingCredential()` in `components/ConnectionForm.tsx` is the one answer both lists use.
- **A key file that cannot be read must not be reported as the server rejecting the key.** `ssh -i` warns about an unopenable identity file on stderr and carries on without it, so the run ends as "Permission denied (publickey)" and `translateSshFailure` blames the far end for a file that was never opened - measured during the alpha test, where the public key had not reached the server yet and that was indistinguishable from a wrong path. Both adapters check first now (`access(…, R_OK)` in rsync's `prepareSshEnv`, a wrapped `readFile` in sftp's `sshAuthOptions`) and name the path.
- **`ssh` auth has three methods but `privateKey` has two provenances**: with a `keyPath` the file is read at connect time and nothing is stored; without one the key contents *are* the stored secret (what the pre-split profiles held, and what a pasted key still produces). This matters beyond bookkeeping — rsync needs a key *file*, so it can only be offered for `agent` or `privateKey` with a `keyPath`.

**Credentials are encrypted at rest, never written plaintext, and there is exactly one store.** `connectionsService.ts` keeps every secret — SFTP/FTP passwords, private keys, the GitHub token, webhook URLs — via Electron's `safeStorage` (OS keychain-backed), base64-encoded into `userData/connections.json`. It used to be two stores (`secretsService.ts` plus the token inside `settingsService.ts`), which meant two encryption call sites and a token the renderer had to relay back to main on every marketplace call; `marketplace.search`/`themeMarketplace.list` therefore no longer take a token parameter and resolve it in main via `getGithubToken()`. If `safeStorage.isEncryptionAvailable()` is false, `saveConnection` **throws** rather than falling back to plaintext or silently discarding the secret. `settingsService.ts` now holds no credential at all, but its `saveSettings` is deliberately read-modify-write: a token still awaiting migration (the user can reach Settings before ever opening the marketplace) must survive a save from there — verified.

**Ein Fallback, der nie ansprang (2026-09-02).** Alle drei Fehlerpfade in `rsync.ts` schrieben `translateSshFailure(…) ?? output.trim() ?? "rsync endete mit Code …"`. Das liest sich als dreistufiger Rückfall, ist aber immer nur zweistufig: `String.trim()` liefert einen String, nie `null` oder `undefined`, und `??` greift ausschließlich bei diesen beiden. Der dritte Zweig war damit unerreichbar — ein rsync, das ohne Ausgabe scheitert (abgeschossener Prozess, ein `-e`-Wrapper, der nicht startet), erzeugte einen `Error` mit leerer Nachricht, und die Seite zeigte ein leeres rotes Feld. Nebenbei war genau dieser Text als einziger im Adapter fest deutsch, also auch für die englische Oberfläche. Beides behoben mit `failureMessage()`: eine Stelle, expliziter Leer-Test statt `??`, und der Exit-Code als `mainT('rsyncExitCode')`.

**„Jedes Linux hat rsync oder kann es installieren“ war die falsche Hälfte der Annahme (2026-09-02).** `rsyncBlockReason()` kannte genau einen Grund, warum es keinen rsync zu spawnen gibt: Windows. Der Kommentar daneben schrieb die andere Hälfte als gesetzt fest — macOS bringt openrsync mit, und jedes Linux habe es. Der Alpha-Test hat das auf einem Debian-13-Desktop widerlegt: `rsync` ist dort Priorität *optional* und schlicht nicht da. Das Zielformular bot die Übertragung trotzdem an, und „Diff aktualisieren“ antwortete mit `Error: spawn rsync ENOENT (deploy:diff)` — der rohe Node-Fehler, der weder sagt, was fehlt, noch was hilft. Behoben an derselben einen Stelle, an der die Regel schon lag: `rsyncBlockReason(connection, platform, rsyncAvailable)` mit dem neuen Grund `not-installed`. Der Adapter beantwortet die Frage über `findExecutable('rsync')` unmittelbar vor dem Spawn (rsync kann installiert werden, während die App offen ist), der Renderer über ein neues Feld `rsyncAvailable` an `settings.environment` — bewusst *nicht* in dessen `tools`, weil rsync optional ist und ein Rechner ohne es keine kaputte Umgebung hat, also auch nicht `ok: false` verdient. Gemessen mit einer App, die mit `PATH` ohne `/usr/bin` gestartet wurde: die Meldung nennt jetzt das fehlende Programm und `sudo apt install rsync`.

**Das Zielformular überlebte den Zielwechsel (2026-09-02).** Ein Effekt auf `selectedId` räumte beim
Wechsel schon Diff, Ausschlüsse, Fortschritt und Deploy-Ergebnis weg, mit der Begründung, all das
beschreibe *ein* Ziel und stehe sonst als Aussage über das neu gewählte da. Das offene
Bearbeiten-Formular war genau derselbe Fall und trotzdem nicht dabei: Ziel A bearbeiten, dann Ziel B
anklicken, und im Formular standen weiter Name, Remote-Pfad und Ausschlüsse von A — bis man bei B
noch einmal auf „Bearbeiten“ klickte. Schlimmer als die Anzeige ist, wohin ein Speichern gegangen
wäre: der Entwurf trägt die ID von A, die Seite ringsum redet von B. Im Alpha-Test gefunden.
Öffnen und Schließen laufen jetzt über `openTargetDraft()`/`closeTargetDraft()`, damit der beim
Öffnen genommene JSON-Schnappschuss nicht vom Formular abweichen kann, und jeder Weg, der das
Formular vom Schirm nimmt — Zielwechsel, „+ Neues Ziel“, Löschen des bearbeiteten Ziels — geht durch
`mayDiscardDraft()`. Gefragt wird nur, wenn es etwas zu verlieren gibt: ein unverändertes Formular
schließt lautlos, ein verändertes stellt die übliche native Ja/Nein-Frage. Gemessen im laufenden
Programm: unverändert wechselt die Auswahl und das Formular ist weg; nach einer Änderung im
Namensfeld bleibt beim Klick auf ein anderes Ziel die Auswahl stehen und das Formular offen, weil
die Frage aussteht. Der Dialog selbst ist ein macOS-Sheet und unter Playwright weder sichtbar noch
bedienbar — dass er kommt, ist gemessen, sein Aussehen nicht.

## Der Ziel-Wähler ist eine Radiogruppe (2026-09-03)

„Ziel“ war eine handgebaute Knopfreihe: das gewählte Ziel blau, alle anderen grau, jeder Knopf ein
eigener Tabstopp, und nichts daran sagte, dass es sich um *eine* Wahl aus mehreren handelt — kein
`radiogroup`, keine Pfeiltasten. Genau das ist `SegmentedControl` seit U3, also ist es das jetzt
auch hier. „Neues Ziel“ bleibt außerhalb der Gruppe: ein Ziel anzulegen ist keine der Optionen.

Eine Sache am Primitive musste dafür nachziehen: `flex-wrap`. Bei den vier bisherigen Aufrufern sind
die Optionen eine feste Liste kurzer Namen, hier sind sie Daten — sieben Ziele mit Namen wie
„boxi-os.github.io/quartzcontrol-testing (GIT-BRANCH)“ passen in keine Zeile. Eine umbrechende
Gruppe ist immer noch eine Gruppe; eine überlaufende lässt Optionen hinter dem Kartenrand.

Ohne ausgewähltes Ziel steht `aria-checked` auf jedem Segment auf `false` und die Gruppe bleibt über
den Tabstopp erreichbar — der Fall, den `SegmentedControl` seit U3 ausdrücklich vorsieht, und der
hier der Normalzustand beim Öffnen der Seite ist.

Im Produktions-Build geprüft: eine Gruppe „Ziel“ mit sieben `radio`-Segmenten, Klick wählt und die
Detailzeile darunter folgt, Pfeil rechts verschiebt Auswahl *und* Fokus. Die Rückfrage beim Wechsel
mit offenem Entwurf ist unverändert - sie hängt an `selectTarget`, nicht am Widget - und wurde nicht
erneut ausgelöst, weil sie ein nativer Dialog ist.

**Sieben Ziele passen nicht in eine Leiste (2026-09-06).** Der Ziel-Wähler ist eine Radiogruppe, und das war richtig; seine *Haut* war es nicht. Die gemeinsame graue Leiste setzt voraus, dass die Optionen in eine Zeile passen — `w-fit` kann nicht auf die breiteste umgebrochene Zeile schrumpfen, es nimmt die verfügbare Breite. Gemessen an einem Projekt mit sieben Zielen: 1390 px breit bei 1728 px Fenster, 942 px bei 1280 px, zwei Zeilen, und neben der zweiten 508 px leere graue Fläche. Dazu kam, dass „+ Neues Ziel“ als eigene graue Pille direkt darunter hing und dazuzugehören schien. `SegmentedControl` hat dafür jetzt `variant="chips"`: keine gemeinsame Fläche, jede Option eine eigene umrandete Pille, die gewählte in Akzentfarbe. Ein Umbruch ist damit eine zweite Reihe statt einer Lücke. Die Bedienung ändert sich nicht — Radiogruppe, ein Tabstopp, Pfeiltasten.

Nachgemessen wurde auch, ob es sonst noch auftritt: alle zwölf Radiogruppen der App auf acht Routen bei 1728 und 1280 px Fensterbreite. Elf sind einzeilig mit 0–2 px Spiel; nur der Ziel-Wähler bricht um, weil er als einziger Optionen hat, die der Nutzer selbst benannt hat. Die übrigen bleiben `track`.

**Der Absatz über Zugang und Ziel ist auf einen Satz zusammengezogen (2026-09-06).** Er stand fünf Zeilen lang über der Seite und erklärte Passwortwechsel, Mehrfachnutzung und den Umgang mit gelöschten Dateien, bevor irgendetwas zu sehen war. Was an dieser Stelle gebraucht wird, ist die Trennung selbst: ein Zugang gehört der App, ein Ziel gehört dem Projekt. Der Rest steht im Formular, wo er hingehört.

**Die Seite wählt jetzt selbst ein Ziel, und die Zielart steht als eigene Fläche in der Pille (2026-09-06).** Zwei Nachträge zum selben Durchgang. *Erstens:* `selectedId` startet auf `null` und merkt sich die Auswahl nur für die Sitzung — nach jedem Start stand die Seite also leer da, denn alles unterhalb der Zielliste beschreibt *ein* Ziel. Bei genau einem Ziel gab es dabei nicht einmal eine Wahl zu treffen. Ein Effekt wählt jetzt das erste, wenn keines gewählt ist oder das gewählte nicht mehr existiert; eine getroffene Wahl überschreibt er nie, und nach dem Löschen des gewählten Ziels springt das nächste ein. *Zweitens:* die Zielart stand als `type.toUpperCase()` in Klammern hinter dem Namen — „GIT-BRANCH" und „FOLDER", während die Auswahl im Formular zwei Zentimeter tiefer „Git-Branch" und „Ordner" sagt. Sie ist jetzt eine kleine Fläche in der Pille und benutzt dieselben Übersetzungen wie das Formular, auch in der Schreibweise (kein `uppercase`). `SegmentedControl` hat dafür ein optionales `badge` pro Option; in der `track`-Haut, wo dafür kein Platz ist, hängt es weiter in Klammern hinten dran, damit die Angabe nirgends verlorengeht.
